## 1. 项目目标与硬要求

Rimuru 是基于操作系统 UDP 栈的 Rust 传输协议族，支持 Windows、Linux、macOS、Android、iOS。三层按需启用；使用 L1 的应用不承担 L2/L3 的可靠性和排序状态。平台没有产品优先级，开发顺序可以受手头设备限制，但不能用一个平台的结果替代其他平台验收。

### 1.1 范围合同

| ID | 硬要求 | 可审查的判据 |
|---|---|---|
| R01 | 每个 Endpoint 恰好一个 UDP socket、一个本地 UDP 端口 | 握手、控制、L1/L2/L3、所有 peer/channel 均复用；不得使用 `SO_REUSEPORT` 多 socket、端口条带化或辅助控制端口 |
| R02 | 使用系统 UDP 栈 | v1 不引入 AF_XDP、DPDK、RDMA 或共享内存替代数据通道 |
| R03 | L1 不可靠帧；L2 可靠原子无序消息；L3 按 channel 可靠原子有序消息 | 三层语义分别测试；L3 依赖 L2，L2 依赖 L1，不能误解为 L3 绕过底层独立传输 |
| R04 | 长度字段为 u32 | 协议可表示 `0..=u32::MAX`；实际可接受大小受策略、地址空间和预算限制，不承诺总能分配 4 GiB |
| R05 | L2/L3 不重复增加每个普通 DATA 段字段 | 复用公共帧/分片标识；BEGIN、ACK、FEC 等字节单独记账 |
| R06 | L3 只有消息语义 | 不提供字节流/Stream；首版 Whole 交付，不以增量前缀冒充完整消息 |
| R07 | 无加密，无外部协议互通 | 不实现 AEAD/AES/ChaCha，不承诺 QUIC/KCP/SRT/UDT 兼容；校验不提供身份认证 |
| R08 | 不以 TCP 公平性作为 v1 KPI | 仍需路径限速、拥塞响应及失联退避；不能推导成“公网无限速发送” |
| R09 | 高丢包、高 RTT、叠加场景必须纳入验收 | 保留 `p≤20%`、`RTT≤500ms` 的范围；按第 11 节统一口径报告目标与结果 |
| R10 | 所有资源有界 | 内存、线程、队列、peer、channel、帧上下文、重试、控制帧均有预算与失败行为 |
| R11 | 参数自治与能力回退 | Supported/Unsupported/Unknown 带证据；安全 bootstrap、边界、迟滞、冻结和回滚 |
| R12 | 提供完全线程安全的 C FFI，头文件由 cbindgen 导出 | Endpoint 等共享句柄可跨任意线程并发使用；原生 async/CQ、竞态与 C/C++ ABI 验证进入验收 |

一个通信对通常有两个 Endpoint，因此全测试可以有两个 UDP socket，每端各一个。本约束不是“整个测试只准一个 socket”。单 socket 双栈可用时使用双栈；若某平台需要分别开 IPv4/IPv6 socket，则同一个 Endpoint 只能选择一种地址族，不能悄悄变成双 socket。系统 DNS 等外部设施与 Rimuru 自有传输资源分开记录，基准使用数值地址。

### 1.2 新增工程合同

| ID | 用户要求 | 落地规则 |
|---|---|---|
| E01 | 可使用 mimalloc；必要时自写及多 Allocator | allocator选型由实现和实测决定，不提供手动feature；全局allocator、消息池、临时arena可分工，遵守跨边界释放规则 |
| E02 | HashMap 使用 hashbrown | 项目代码的散列表用 `hashbrown::HashMap`；不引入 `std::collections::HashMap` 自建替代路径 |
| E03 | Mutex HashMap 使用 DashMap | 需要共享并发散列表时用 `DashMap`，也不以 `RwLock<HashMap>` 规避要求；它不是无锁容器 |
| E04 | 数字 Key 自定义直接 Hasher | 支持范围内 `finish()` 直接返回整数位表示，不执行通用混合算法；适用条件与退化风险见第 7 节 |
| E05 | 不要求抗哈希攻击 | 非数字键可用高性能非加密算法；“最快”由真实键分布/CPU/整表操作测量，不凭宣传定论 |
| E06 | Bits 使用 bitvec 或 bitfield | 固定位域优先现有 bitfield，动态位图采用bitvec；并发发布规则单独设计，不等同普通位图读写 |
| E07 | 结构体定义使用 zerocopy | 线格式及可安全映射的固定布局结构使用 zerocopy 类型/derive；有指针、锁、Arc、有效值约束的运行时对象按 Rust 所有权定义，不能强行字节反序列化 |
| E08 | 性能可换取部分资源，也要压缩资源 | 同时报告 CPU、峰值/稳态内存、碎片、线程、线字节与尾时延；超预算的吞吐提升不能作为默认优化 |
| E09 | 优先成熟权威 crate，细节压榨性能 | 优先维护良好、文档/测试明确的组件；自写只限协议必需逻辑与证据支持的窄范围热点 |
| E10 | 使用 rayon 添加并发能力 | CPU 数据并行统一用 Rayon；有界线程池、工作粒度阈值、串行对照，避免与 I/O 线程过度订阅 |
| E11 | 极致优化 FFI 轮询/async | 自研完成队列与 arm/recheck 通知合同；系统原生可等待对象；批量提交/收割，不按包跨 FFI |
| E12 | FFI 完全线程安全 | 带 generation 的句柄、调用 pin、MPMC完成队列；并发 send/poll/close/release 安全；不要求回到创建线程 |

第三方 crate 的内部实现不受项目源码选型条款逐项改写；应审计依赖树与成本，不 fork 整个生态去替换内部容器。E02/E03 也不强迫把适合数组、slab、有序树的数据结构改成散列表。


## 2. 原设计需要纠正的关键点

| 原表述/问题 | 本稿修订及原因 |
|---|---|
| “默认永远7B头”，重连只加可选1B epoch | wire v1冻结8B方向身份，DATA16/32分别15/17B；类型直接指明索引宽度，不伪称仍是7B |
| DATA_R自描述但索引宽度须依赖BEGIN，flags未定义 | DATA16/32占两个明确type，BEGIN再校验idx_bytes；未知身份拒绝 |
| token 用 LRU 直接复用，隐式计数模式零丢包时可开 | LRU 不能防止迟到段写入新帧；隐式模式会在下次丢包/乱序前已经误映射。两者移出首版正确性路径，先解决 generation 与可检测失步 |
| 内核直接收进目标 FrameBuf，跨平台 RX 原地零拷贝 | 通常需先收 datagram、解析头，再决定目标偏移；portable 路径承认一次用户态重组拷贝。Scatter 片段借用与 contiguous Whole 的成本分开验收 |
| Linux loopback 用 MSG_ZEROCOPY 消除 TX 拷贝 | 内核文档说明本地 loopback 会 deferred copy；仅设置 flag 不证明无拷贝，必须查完成通知及实际 copy fallback [S7] |
| CAS 未收→已收，然后才复制；Scatter 可立即读 | 增加“写入中/已发布”状态，复制和校验结束后 Release 发布，读者 Acquire；不能先置 ready 再写入 |
| 完成后从 map 删除并直接释放接收预算 | 保留去重墓碑；L3、事件队列和应用持有的实际缓冲仍计预算，最后引用释放才退还内存 |
| credit 是当前空闲字节，重传无限豁免 | 改成消息预留授权、幂等 grant、单调额度。只对仍持有授权的已准入消息允许不再消耗新 credit；重传仍受 pacing/cwnd/CPU 限制 |
| L1 在任意高丢包下 Whole goodput 仍 ≥90% raw UDP | 不重传的 n 段帧完整概率为 `(1-p)^n`（独立丢包）。改为有损时分别报告 segment goodput 与完整帧 goodput，不能沿用错误等价关系 |
| L3 数据段不加字节，所以吞吐必然相同 | 零额外 DATA 字节只说明编码性质；元数据、排序、背压、内存与 HOL 都可能降吞吐，必须实测 |
| channel元数据约3–6B/消息 | v1 BEGIN统一固定channel:u16/seq:u32等字段，占位成本如实计；L3不相对L2另加字段 |
| “一个 RTT 替换所有默认值”，生产启动标定 raw UDP | 改为样本足够才调优，允许 bootstrap 长期保持；raw UDP 饱和标定放离线基准，不在生产启动额外开端口或灌满链路 |
| 无锁竞争、零分配是绝对前提 | 改为可测目标：预热后、声明容量内每 DATA 路径不向通用 allocator 申请；共享表锁与队列竞争必须统计，不虚称 DashMap 无锁 |
| 随机丢包与拥塞可以准确区分；FEC 总是必须 | 分类有不确定性，缺证据按保守拥塞处理；ARQ 足够流水化也可高吞吐，FEC 以净收益启用 |
| FEC 吞吐公式同时乘 `(1-p)` 又除 `(1+r)` | 改用源符号数/总发送符号数、实际成功交付及 CPU 成本统计；避免重复计算损失；块等待与解码时延绝不记为零 |
| NACK 总能快一个量级、TLP 必带新数据 | 都不能保证：NACK 仍需传播与等待；没有新数据时必须可探测/补发尾部；ACK 丢失可能导致不可避免的重复传输 |
| QUIC 的 ACK 与按序应用交付耦合 | 删除不实比较；Rimuru 的分层取舍独立论证，不以错误描述其他协议支撑 |
| Windows 校验和默认关闭、Apple 符号存在即可用 | 不沿用：Windows 选项需核对实际默认与行为；Apple 仅使用当前目标 SDK 的公开 API，动态符号存在不能证明可发布 [S8] |

这些是显式规范修订，不是已经实现的修复。端口、分层、长度、无加密、无 Stream 等产品范围保持；用户授权本次直接决策后，线格式及有损 L1 指标按本版冻结。
